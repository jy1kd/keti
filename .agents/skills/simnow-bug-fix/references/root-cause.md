# 根因调查详解

## 核心原则
**没有完成根因调查就不能修。** 随机修复浪费时间并引入新 bug。

## 阶段 1：理解问题

1. **读 task2.md 中的问题描述** — 理解 bug 的具体表现、复现步骤
2. **读修复方案** — task2.md 中已有详细的修复方案，但必须先理解为什么需要这样修
3. **读涉及文件** — 按 task2.md 列出的文件逐个读取，理解当前实现

## 阶段 2：稳定复现

1. **运行相关测试** — `python -m pytest tests/xxx.py -v` 或 `npm test`
2. **手动复现** — 如果是 UI 问题，启动前端手动操作
3. **确认复现条件** — 每次都能触发？还是偶发？

## 阶段 3：追踪数据流

SimNow 项目的数据流路径：

```
前端组件 → API 请求 → 后端路由 → 业务逻辑 → CTP API → CTP 柜台
                                                    ↓
前端渲染 ← WebSocket ← 后端聚合 ← CTP 回调 ←──────┘
```

按层排查：
- **前端层**：组件状态、API 调用参数、响应处理
- **API 层**：路由定义、请求/响应 model、字段映射
- **后端层**：业务逻辑、CTP API 调用、错误处理
- **CTP 层**：字段值、枚举映射、回调处理

## 阶段 4：形成假设

明确写出假设：
```
假设：X 是根因，因为 Y
证据：[具体的代码行、测试输出、错误信息]
验证方法：[最小改动测试]
```

## 阶段 5：验证假设

- 最小改动测试 — 一次只改一个变量
- 如果假设不成立 → 回阶段 1 重新分析
- 如果 3 次假设都失败 → 停下来质疑架构，和用户讨论

## 输出格式

```
📌 [simnow-bug-fix]

🔍 根因调查报告

Bug：[简述]
复现：[稳定/偶发] — [复现步骤]

根因分析：
- 问题位置：[文件:行号]
- 根因：[为什么出错]
- 影响范围：[哪些功能受影响]

假设验证：
- 假设：[X 是根因因为 Y]
- 验证结果：[通过/失败]

可以开始修复。
```
