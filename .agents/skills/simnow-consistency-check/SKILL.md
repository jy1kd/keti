# SimNow 一致性检查

## 功能
从专业金融交易系统开发视角，执行五维一致性检查：

1. **代码 ↔ 文档一致性**：API 路由 vs design.md、组件 vs prd.md、数据结构 vs dev.md
2. **进度同步**：git log vs task.md 状态是否同步
3. **前后端契合度**：字段名对齐、业务流程链路完整性、金融专业性
4. **前后端数据流一致性**：追踪「前端请求 → 后端接收 → 处理 → 响应 → 前端解析 → 展示」全链路，验证字段名/类型/值域/枚举是否全程一致
5. **运行时行为**：时间戳时区、并发安全、WebSocket 生命周期、hook 单例、重入保护
6. **代码质量**：死代码、类型定义准确性、重复代码、魔法值

## 执行流程

### 第零步：断点续跑检查
📌 [simnow-consistency-check]

每次调用时，先明确报告路径，再决定是继续还是重新检查：

1. **明确报告路径**（⚠️ 不要自己猜，必须让用户确认）：
   - 执行 `ls docs/check*/report.md 2>/dev/null` 列出所有已有报告
   - 执行 `git branch --show-current` 获取当前分支名
   - 向用户展示所有已有报告及其对应分支，例如：
     ```
     已有检查报告：
     1. docs/check01/report.md ← check/docsCheck01（6项，2已修复）
     2. docs/check03/report.md ← check/docsCheck03（8项，0已修复）
     当前分支：fix/xxx
     请问要操作哪个报告？输入编号或路径：
     ```
   - 用户选定后，读取该报告

2. **展示当前报告的问题清单**（⚠️ 先展示，不要一上来就检测）：
   - 读取报告，按 PR 编号逐项列出，格式：
     ```
     当前报告问题清单（docs/check03/report.md）：
     ┌─────┬──────────────────────────────────┬──────┬────────┐
     │ 编号 │ 问题描述                          │ 等级  │ 状态    │
     ├─────┼──────────────────────────────────┼──────┼────────┤
     │ #1  │ cancelAllOrders 前后端响应字段不匹配 │ 🔴 P0 │ ⏳ 待处理 │
     │ #2  │ K线时间戳前后端不一致               │ 🔴 P0 │ ⏳ 待处理 │
     │ #3  │ submitOrder 缺少 exchangeID       │ 🔴 P1 │ ⏳ 待处理 │
     │ ... │ ...                              │ ...  │ ...    │
     └─────┴──────────────────────────────────┴──────┴────────┘
     ```
   - 统计摘要：X 项待处理 / Y 项已修复 / Z 项暂不处理

3. **让用户选择操作方式**：
   - **逐条处理** → 进入第五步，从第一个「⏳ 待处理」项开始（推荐）
   - **重新检查** → 执行完整的第一步~第四步（会覆盖旧报告）
   - **指定某几项** → 只处理用户选中的编号

4. 如果报告不存在 → 执行完整的第一步~第四步

### 第一步：检查分支 & 收集信息

1. **⚠️ 检查当前分支**
   - 执行 `git branch --show-current` 获取当前分支名
   - 如果当前不在 `check/` 分支（如 `check/docsCheck01`），则：
     - 执行 `git branch --list "check/docsCheck*"` 查看已有的 check 分支
     - 提示用户："当前不在检查分支上。已有的检查分支：xxx。建议创建新分支 check/docsCheckNN，请手动执行：`git checkout -b check/docsCheckNN`"
     - **不要自动创建分支，必须由用户手动执行**
     - 等待用户创建分支后再继续
2. 执行 `git log --oneline -20` 了解实际开发进度
3. 读取 docs/ 目录下的文档：prd.md、design.md、dev.md、task.md
4. 默认全量扫描前端和后端代码（**不读 knowledge-graph.json，以实际代码为准**）。用户主动缩小范围时（如"只查前端"），只扫描对应部分

⚠️ **检测原则：必须读实际代码文件，不能只读文档或凭印象判断。每个结论都要有代码证据（文件路径 + 行号 + 实际代码片段）。**

### 第二步：代码 ↔ 文档双向检查
分两个方向扫描：

**方向 A：代码 ↔ 文档一致性（以实际代码为准）**
- 以 `server/main.py` 路由注册为 API 真实来源，对比 design.md 是否一致
  - 具体方法：`grep` 搜索 `@app.(get|post|put|delete)` 提取所有路由，与 design.md 中的 API 列表逐条对比
- 以 `frontend/src/` 实际组件为功能真实来源，对比 prd.md 是否有对应需求
  - 具体方法：扫描 `frontend/src/pages/` 和 `frontend/src/components/` 目录结构，与 prd.md 功能列表逐条对比
- 以代码中的数据结构为真实来源，对比 dev.md 中的数据模型定义是否一致

**方向 B：进度同步检查（git log vs task.md）**
- 对照 `git log --oneline -20` 中的 commit 记录，检查 task.md 中的 PR 状态是否落后
- 已有 `feat(task-xx)` / `Merge pull request` commit 但 task.md 标记为「⏳ 待开始」→ 文档进度落后
- 已有 `docs(task-xx): 人工验证通过` 但 task.md 未标记「✅ 已完成」→ 文档进度落后
- 已合并到 main 但 progress.md 未更新 → 文档进度落后

### 第三步：前后端契合度检查
从金融交易系统专业视角，检查前后端是否对齐：

**API 契合度（含字段名一致性）**
- 后端返回的字段，前端是否都用到了？是否有遗漏？
- 前端请求的参数，后端是否都支持？是否有缺失？
- **字段名一致性**：对比后端 Pydantic model / API 响应的字段名 vs 前端请求/解析代码中的字段名，不能出现后端命名 `a`、前端调用 `b` 的情况
- 错误处理：检查 `server/main.py` 的异常处理逻辑 + 前端 fetch 调用的 error handling 是否匹配

**业务流程契合度**

逐段验证关键节点，每段必须找到代码证据，不能凭印象判断：

| 流程 | 关键节点 | 验证方法 |
|------|----------|----------|
| 报单 | 前端表单提交 → API 路由 → CTP 报单 → 回报推送 → 前端更新 | 分段验证：① grep 前端提交函数找到对应 API 路由 ② grep 后端路由找到 trader_api 调用 ③ grep WebSocket 推送逻辑 ④ grep 前端订阅和更新逻辑 |
| 行情 | CTP 订阅 → 行情聚合 → WebSocket 推送 → 前端渲染 | 分段验证：① grep md_user_api 订阅方法 ② grep 行情数据处理/聚合逻辑 ③ grep /ws/market 推送 ④ grep 前端行情组件渲染 |
| 查询 | 前端触发 → API 路由 → CTP 查询 → 结果返回 → 前端展示 | 分段验证：① grep 前端查询触发函数 ② grep 后端查询路由 ③ grep trader_api 查询方法 ④ grep 前端展示组件 |

**金融专业性检查（参考无限易等产品）**

逐项检查，每项必须找到代码证据再下结论，不能凭印象判断：

| 检查项 | 验证位置 | 检查内容 |
|--------|----------|----------|
| 报单功能 | `server/ctp_wrapper/trader_api.py` | 是否支持限价/市价、开仓/平仓、GFD/FOK/FAK |
| 五档行情 | `frontend/src/` 中行情组件 + `server/ctp_wrapper/md_user_api.py` | 买一到买五、卖一到卖五是否完整传递和展示 |
| 持仓展示 | 前端持仓组件 + 后端 `/api/position` | 是否包含：持仓量、开仓均价、浮动盈亏、保证金 |
| K 线图 | 前端 K 线组件（ECharts） | 是否支持多周期切换、均线指标、缩放状态保持 |
| 止损单 | 后端止损监控服务 + `docs/specs/design.md` | 逻辑是否合理：价格触发 → 自动报单 → 状态跟踪 |

### 第三步（续）：前后端数据流一致性检查

追踪关键数据从前端到后端再回到前端的完整链路，验证字段名、类型、值域是否全程一致：

**数据流追踪方法**

对每个业务流程，按「前端请求 → 后端接收 → 后端处理 → 后端响应 → 前端解析 → 前端展示」六步逐段验证：

| 流程 | 追踪链路 | 验证要点 |
|------|----------|----------|
| 报单提交 | 前端表单字段 → API request model → CTP field → 回报 → 前端解析 | 字段名是否一致？枚举值是否对齐（如 direction "0"/"1" vs "buy"/"sell"）？必填/可选是否匹配？ |
| 止损单 | 前端参数 → SubmitStopOrderRequest → stop_order store → 触发报单 | exchangeID 是否传递？price 字段单位是否一致？ |
| 撤单 | 前端 orderRef → API → CTP → 响应 → 前端更新 | orderRef/orderSysID 混用？cancel 响应字段是否与前端类型定义匹配？ |
| 查询结果 | CTP 返回 → 后端转换 → API 响应 → 前端类型 → 展示 | 后端 camelCase 转换是否完整？前端类型定义是否与实际响应匹配？ |
| 行情推送 | CTP tick → 后端处理 → WebSocket → 前端 hook → 组件 | 前后端字段名是否一致？时间戳格式是否统一？ |

**具体检查项**

1. **字段名对齐**：对比后端 Pydantic model 的字段名 vs 前端 TypeScript interface 的字段名，逐字段验证
2. **枚举值对齐**：CTP 使用 char 值（"0"/"1"/"2"），后端是否转换？前端是否正确处理？类型定义是否反映实际值？
3. **默认值一致性**：后端 `Field(default=...)` 的默认值，前端是否有对应处理？
4. **响应结构匹配**：后端实际返回的 JSON 结构 vs 前端 `api.ts` 中定义的 response type，是否完全匹配？

### 第三步（续）：运行时行为分析

分析代码在运行时的实际行为，发现静态检查无法捕获的问题：

**时间戳与时间计算**

| 检查项 | 验证方法 | 常见问题 |
|--------|----------|----------|
| CTP 时间解析 | grep `calendar.timegm` / `datetime` / `Date(` | CTP 返回中国时间（UTC+8），`calendar.timegm` 按 UTC 处理导致偏差 8 小时 |
| 时间戳单位 | grep `timestamp` / `updateTime` | 混用秒级/毫秒级时间戳 |
| 前端时间解析 | grep `new Date(` / `Date.parse` | 字符串时间无时区后缀被当作本地时间 |
| K 线时间对齐 | 对比 REST 和 WebSocket 两条路径的时间处理 | 两条路径使用不同时间解析逻辑导致 K 线数据不一致 |

**并发与状态安全**

| 检查项 | 验证方法 | 常见问题 |
|--------|----------|----------|
| WebSocket hook 单例 | grep `new WSManager` / `useMarketWs` | 每个组件实例创建独立连接，导致重复连接和数据不同步 |
| 刷新重入保护 | grep `setInterval` / `refreshAll` | 长耗时操作（>10s）未防重入，interval 叠加导致请求堆积 |
| 止损单竞态条件 | 阅读止损触发逻辑的锁机制 | lock 在条件检查和触发动作之间释放，导致并发触发 |
| CTP 查询限流 | 检查查询服务是否有节流/串行化 | 并发查询 CTP 柜台导致响应丢失或超时 |
| 状态机一致性 | 检查 connection/login 状态转换逻辑 | reconnect 时 reconnectCount 赋值错误（MD/TD 共享同一变量） |

**WebSocket 生命周期**

| 检查项 | 验证方法 | 常见问题 |
|--------|----------|----------|
| 连接管理 | 阅读 ws.ts 连接/断开/重连逻辑 | onopen 被覆盖（dead code）、onclose 未清理资源 |
| 消息分发 | 检查 onmessage handler | 消息类型路由是否完整？未知消息是否处理？ |
| 多端点隔离 | 检查 /ws/market、/ws/order 等是否独立 | 端点间状态互相干扰 |

### 第三步（续）：代码质量检查

发现死代码、类型定义不准确、重复代码等质量问题：

**死代码检测**

| 检查项 | 验证方法 | 常见问题 |
|--------|----------|----------|
| 未调用的函数 | grep 函数名，检查是否有调用方 | 定义了转换函数但从未使用 |
| 未使用的导入 | 检查 import 语句 | 导入了模块但未使用 |
| 未调用的路由注册 | grep `wire_ctp_*_bridge` 调用 | 定义了桥接函数但从未注册到 app |
| 死亡代码路径 | 检查条件分支 | 某些分支永远不会执行 |

**类型定义准确性**

| 检查项 | 验证方法 | 常见问题 |
|--------|----------|----------|
| 枚举值覆盖 | 对比 TypeScript union type vs 实际值 | 类型定义 `'buy' | 'sell'` 但实际收到 `"0" | "1"` |
| 可选字段标记 | 对比 TypeScript `?` vs 后端 `Optional` | 前端标记必填但后端可能返回 null |
| 重复类型定义 | grep 类型名，检查是否有多个同名定义 | `OrderRecord` 和 `OrderStatus` 重复定义 |
| 响应类型覆盖 | 对比 api.ts response type vs 实际 JSON | 类型定义了 `cancelled` 但后端返回 `succeeded` |

**代码重复与一致性**

| 检查项 | 验证方法 | 常见问题 |
|--------|----------|----------|
| 重复逻辑 | 搜索相似代码模式 | 多处相同的 K 线时间转换逻辑 |
| 命名一致性 | 对比同类功能的命名风格 | 同一概念在不同文件使用不同命名 |
| 魔法值 | grep 硬编码的字符串/数字 | 直接使用 `"CFFEX"` 而非从配置读取 |

### 第四步：生成检查任务清单

⚠️ **流程：先扫描 → 输出问题清单 → 用户确认 → 再写入报告 → 进入第五步逐条详细检测**

按严重等级分类汇总所有发现的问题，生成任务清单：

```
📌 [simnow-consistency-check]

## 一致性检查报告

### 🔴 阻断性问题（必须修复）
1. [问题描述] — 实际文件路径 / 建议方案（⚠️ 必须写实际文件路径和行号，不能留占位符）

### 🟡 不一致问题（建议修复）
1. [问题描述] — 实际文件路径 / 建议方案（⚠️ 必须写实际文件路径和行号，不能留占位符）

### 🔵 改进建议（可选）
1. [问题描述] — 参考无限易等产品的做法
```

将清单展示给用户确认，确认后写入检查文档。检查文档路径规则：根据当前分支名确定，如分支为 `check/docsCheck01` 则写入 `docs/check01/report.md`。检查文档包含完整的检查结果和每项的处理状态。

⚠️ **注意：第四步只是汇总问题清单（概览），不逐条深入验证。逐条读代码验证在第五步进行。**

### 第五步：逐条确认并执行
⚠️ **必须逐条处理，确认一项后才能开始下一项，不可跳过或批量处理**

⚠️ **核心原则：本 skill 禁止直接修改代码（frontend/ 和 server/）。所有代码改动必须以 PR 形式写入 task2.md，由专门角色后续执行。**

对清单中的每一项，严格按以下顺序执行：

#### 5.0 展示当前问题
向用户展示该项的问题描述、严重等级、涉及文件，例如：
```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📌 第 #1 项 / 共 N 项
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
问题：cancelAllOrders 前后端响应字段不匹配
等级：🔴 P0
影响：批量撤单 toast 显示 "已撤销 undefined 笔报单"
涉及文件：
  - frontend/src/services/api.ts:275-280
  - server/services/order_manager.py:401-404
```

#### 5.1 阅读实际代码确认问题是否存在（⚠️ 必须读代码，不能只读文档或凭记忆）
- 用 Read 工具读取问题涉及的实际文件（前端+后端都要读）
- 对比报告中的问题描述 vs 实际代码
- **必须展示实际代码片段**，不能只说"问题存在"
- 如果问题已修复（其他窗口可能已改），展示修复证据，标记「✅ 已修复」，跳过

#### 5.2 输出检测结论 + 建议方案
展示检测结果：
```
🔍 检测结果：问题 [存在 / 已修复 / 部分存在]

实际代码（frontend/src/services/api.ts:275）：
  const result = await response.json()
  toast.success(`已撤销 ${result.cancelled} 笔报单`)  // ← cancelled 不存在

期望代码：
  toast.success(`已撤销 ${result.succeeded} 笔报单`)  // ← 后端返回 succeeded

建议方案：
  → 修改前端字段名 cancelled → succeeded（文档修改 / 代码修改）
```

#### 5.3 提供用户验证步骤（⚠️ 必须给出手动验证步骤，由用户自行确认）
```
🔍 请手动验证：
1. 打开 frontend/src/services/api.ts，定位到第 275 行
2. 确认当前代码中 result.cancelled 是否确实存在（而非 result.succeeded）
3. 如需验证后端实际返回，可运行：
   curl -X POST http://localhost:8000/api/order/cancel-all | python -m json.tool
   检查返回 JSON 中的字段名
```

#### 5.4 等待用户确认（⚠️ 用户确认后才能进入下一项）
- 等待用户回复，用户可能：
  - **确认问题存在** → 继续处理（修改文档 / 写入 task2.md）
  - **已自行修复** → 标记「✅ 已修复」，跳过
  - **暂不处理** → 标记「⏭️ 暂不处理」，记录原因
  - **有疑问** → 补充说明，再次验证

#### 5.5 执行修改
确认后立即执行：
- **修改文档** → 直接更新 docs/ 下的文件（design.md、dev.md、prd.md、task.md 等）
- **修改代码** → 将代码修改计划写入 `docs/tasks/consistency-check-records.md`，格式见下方模板
- **暂不处理** → 记录原因到检查文档

#### 5.6 更新报告状态
