# 验证规则

## 自验证（TDD 开发完成后）

### 流程
1. 从 task.md 提取验收标准
2. 逐条对比验收标准与实际代码：
   - ✅ 已实现
   - ❌ 遗漏（task.md 要求了但没做）
   - ⏸️ 推迟到其他 PR
3. 遗漏/推迟项展示给用户，等待决定：
   - 立即实现 → 回到开发
   - 确认推迟 → 记录到 dev-record-a.md
4. 逐条验证，每次只讨论一项
5. 验证维度：核心功能、正常路径、异常路径、调试代码清理、范围控制、文档同步
6. 未通过 → 回到第 2 步 TDD 开发修复 → 重新自验证

### 完成后
- 更新 progress.md 状态为「开发完成，待审查」
- commit
- 提示用户切换审查窗口

## 人工验证（审查通过后）

### ⚠️ 核心原则
**人工验证 ≠ 跑自动化测试。** 目的是让用户亲自在浏览器/终端中确认功能可用。
- 禁止直接运行 pytest、npm test 或其他自动化测试
- 必须输出具体的 curl 命令、浏览器 URL、Swagger 页面操作步骤
- 每次只给一条验证项，等用户反馈后再给下一条

### 第一步：生成验证清单
1. 从 task.md 提取当前 PR 的「验证方法」和「验收标准」
2. 读取 Swagger 文档（http://localhost:8000/docs#/）确认接口参数
3. 根据实际代码补充 task.md 未覆盖的功能点
4. 列出推迟项
5. 输出清单，每条标记「待验证」，**等待用户确认清单后再开始逐条验证**

### 第二步：逐条验证
**每次只输出一条验证项**，格式如下：
```
### 验证项 N/M：[功能名称]

**前置条件：** [需要先做什么，如"确保后端已启动"]

**验证步骤：**
1. [具体操作，如：浏览器访问 http://localhost:8000/api/market/instruments]
2. [或：在 Swagger 页面找到 POST /api/market/subscribe，点击 Try it out，输入参数...]

**预期结果：** [具体的返回值或页面表现]

**请执行后告诉我结果：** ✅ 通过 / ❌ 不通过（附上实际输出）
```

等待用户反馈后：
- ✅ 通过 → 记录到 verify-discussion-prX.md，输出下一条
- ❌ 不通过 → 分析原因 → 修复代码 → 重新验证该项

### ⚠️ 每验证完一条，必须立即执行：
a. 记录到 verify-discussion-prX.md（验证项、步骤、结果、问题 + 业务讨论）
b. 然后才能进入下一条

### 全部验证完成后（批量 commit）
- 将所有验证记录一次性 commit：`docs(task-xx): 人工验证记录 - PR-X`
- 避免每条验证单独 commit 产生噪声
- 如验证过程中有代码修复，修复代码单独 commit，验证记录最后批量 commit
- 更新 progress.md 状态为「人工验证通过，待收尾」
- 推迟项记录到 dev-record-a.md
- commit
