# 审查规则

## 审查前准备（审查窗口）
1. git pull 确保最新（**⚠️ 如遇冲突，停止并提示用户解决**）
2. 确认当前任务来源（task.md 或 task-redesign.md），从对应任务文件读取 PR 信息和状态
3. git status 确认工作区干净
4. git diff main...feature/pr-x 获取改动范围
5. 状态不对 → 终止审查并提示原因
6. **如任务文件状态与 git log 不一致，以 git log 为准，提示用户可能有另一个窗口在操作**

## 执行审查
1. 按严重等级分三类：
   - 🔴 阻断性问题（必须修改才能合入）
   - 🟡 改进建议（不阻塞合入）
   - 🔵 疑问确认
2. 审查维度：功能正确性、测试质量、代码质量、范围控制、文档同步、潜在风险、task.md 完整性
3. 多轮审查追加到同一文件，按轮次区分

## ⚠️ 必须先写文件再给结论
- **必须先将审查结果写入 review-feedback-b-prX.md**
- **然后才能给出审查结论**（结论必须与文件内容一致）
- 防止跳过写文件直接说"通过"

## 审查后提示
- 提示开发窗口 commit review-feedback
- 通过 → 提示开发窗口执行人工验证
- 不通过 → 提示开发窗口处理审查反馈

---

## 审查反馈处理（开发窗口）

### 流程
1. 读取 review-feedback-b-prX.md
2. 逐条处理：
   - 🔴 必须修复，每修复一个单独 commit
   - 🟡 认同则改/不认同则记录理由，可批量 commit
   - 🔵 补充解释
3. 更新 review-reply-b-prX.md、dev-record-b.md、progress.md：
   - 有 🔴 → 「修复完成，待二次审查」
   - 只有 🟡 → 「改进建议已处理，待确认合并」
4. commit

### 回退说明
- 🔴 修复时**不需要重新跑完整 TDD 循环**
- 仅针对审查指出的问题做定向修复
- 但修复代码**必须有对应测试**（可以补测试，也可以验证已有测试覆盖）
- 修复后直接走自验证，不回到 TDD 开发步骤

### 完成后
- 更新任务文件中 PR 状态为「修复完成，待二次审查」
- 提示用户切换审查窗口做二次审查
