### 2.4 关键路径

**关键路径**（最长依赖链，决定项目总工期）：
```
PR-1 [A] → PR-3 [A] → PR-5 [A] → PR-7 [A] → PR-9 [A] → PR-11 [A] → PR-13 [A] → PR-16 [B] → PR-17 [A+B]
```

**关键路径工期**：2+2+3+2+3+2+3+3+3 = 23小时

**并行优化**：
- 角色B的PR-2、PR-4、PR-6、PR-8、PR-10、PR-12、PR-14可与角色A并行
- PR-15依赖PR-9和PR-10，需等待PR-9完成后才能开始
- PR-16依赖PR-11和PR-13，需等待两者都完成后才能开始
- 实际总工期取决于关键路径 + 角色B的额外工作量

**注意**：PR-13依赖PR-9（不依赖PR-11），因此PR-11和PR-13可以并行开发

## 4. 提交时机规范

### 4.1 何时提交

每个PR完成以下工作后应立即提交：

| 时机 | 说明 | 提交内容 |
|------|------|----------|
| **功能完成** | PR描述中的所有功能点实现完毕 | 代码 + 更新task.md状态 |
| **验证通过** | PR验证方法中的所有检查点通过 | 代码 + 测试记录 |
| **代码审查** | 自审或团队审查通过 | 代码 + 审查意见 |
| **每日结束** | 当天工作结束时（即使未完成） | 代码 + 进度说明 |

### 4.2 提交规范

```bash
# 提交格式
git add .
git commit -m "<type>(<scope>): <subject>

- 完成的功能点1
- 完成的功能点2
- 验证结果

Refs: PR-<编号>"
```

**提交类型**：
- `feat`: 新功能
- `fix`: Bug修复
- `docs`: 文档更新
- `style`: 代码格式调整
- `refactor`: 重构
- `test`: 测试相关
- `chore`: 构建/工具相关

### 4.3 提交后更新

每次提交后必须更新以下文件：

1. **task.md**：更新对应PR的状态
   ```markdown
   | 状态 | ✅ 已完成 |
   ```

2. **snapshots/role-a/progress.md** 或 **snapshots/role-b/progress.md**：记录完成情况
   ```markdown
   ### PR-X: 标题
   - 状态：✅ 已完成
   - 完成时间：YYYY-MM-DD
   - 提交记录：commit hash
   - 验证结果：通过
   ```

## 5. 分支合并顺序

### 5.1 分支策略

```
main (主分支)
  │
  ├── feature/pr-1-ctp-verify        (PR-1分支)
  ├── feature/pr-2-frontend-init     (PR-2分支)
  ├── feature/pr-3-fastapi-framework (PR-3分支)
  ├── feature/pr-4-layout-framework  (PR-4分支)
  └── ...
```

### 5.2 合并顺序

**原则**：按PR编号顺序合并，依赖关系必须满足后再合并。

**合并流程**：

```
1. PR-1完成 → 合并到main
2. PR-2完成 → 合并到main（可与PR-1并行）
3. PR-3完成 → 合并到main（依赖PR-1）
4. PR-4完成 → 合并到main（依赖PR-2）
5. PR-5完成 → 合并到main（依赖PR-3）
6. PR-6完成 → 合并到main（依赖PR-4）
7. ...以此类推
```

### 5.3 合并检查清单

每个PR合并前必须满足：

- [ ] 代码功能完整（PR描述中的所有功能点）
- [ ] 验证方法通过（PR验证方法中的所有检查点）
- [ ] 无编译错误（TypeScript/Python）
- [ ] 无Lint错误（ESLint/Black）
- [ ] 依赖PR已合并（检查PR依赖关系）
- [ ] task.md状态已更新

### 5.4 合并命令

```bash
# 切换到main分支
git checkout main

# 拉取最新代码
git pull origin main

# 合并feature分支
git merge feature/pr-<编号>-<描述>

# 推送到远程
git push origin main

# 删除feature分支（可选）
git branch -d feature/pr-<编号>-<描述>
```

## 10. 快速判断指南

### 10.1 AI接手时

1. **读取task-dev-flow.md**：了解当前阶段和状态
2. **读取snapshots/role-a/progress.md** 或 **snapshots/role-b/progress.md**：了解已完成的PR
3. **查看task.md**：找到下一个待开始的PR
4. **检查依赖关系**：确认依赖的PR已合并
5. **开始开发**：按照PR描述实现功能

### 10.2 团队成员接手时

1. **查看当前阶段**：确定自己角色的任务
2. **查看snapshots/progress.md**：了解已完成的PR
3. **找到下一个PR**：按照任务清单顺序
4. **检查依赖**：确认依赖的PR已合并
5. **创建feature分支**：`git checkout -b feature/pr-<编号>-<描述>`
6. **开始开发**：按照PR描述实现功能
7. **完成后更新**：提交代码，更新task.md和progress.md

### 13.2 关键发现

**SubscribeMarketData参数格式问题**：

```python
# ❌ 错误：bytes列表导致堆损坏崩溃(0xC0000374)
api.SubscribeMarketData([b"IF2608"])

# ✅ 正确：必须传字符串列表
api.SubscribeMarketData(["IF2608"])
```

原因：ctp-python的SWIG绑定处理bytes时内存越界。

**影响范围**：所有Subscribe/Unsubscribe方法都受影响，包括：
- `SubscribeMarketData`
- `UnSubscribeMarketData`
- `SubscribeForQuoteRsp`
- `UnSubscribeForQuoteRsp`

### 13.5 真实API字段结构

**字段来源**：`docs/ctp-api-structure.txt`

已通过SWIG反射探测的CTP字段结构（19个核心类）：

| 类型 | CTP类名 | TypeScript接口 | 字段数 |
|------|---------|---------------|--------|
| 登录请求 | CThostFtdcReqUserLoginField | LoginRequest | 11 |
| 登录响应 | CThostFtdcRspUserLoginField | LoginResponse | 15 |
| 行情快照 | CThostFtdcDepthMarketDataField | MarketSnapshot | 50+ |
| 报单请求 | CThostFtdcInputOrderField | OrderRequest | 30+ |
| 报单回报 | CThostFtdcOrderField | OrderReturn | 50+ |
| 成交回报 | CThostFtdcTradeField | TradeReturn | 30+ |
| 撤单请求 | CThostFtdcInputOrderActionField | CancelOrderRequest | 18 |
| 持仓信息 | CThostFtdcInvestorPositionField | PositionInfo | 40+ |
| 账户资金 | CThostFtdcTradingAccountField | AccountInfo | 40+ |
| 合约信息 | CThostFtdcInstrumentField | InstrumentInfo | 30+ |

**自定义业务接口**（CTP无原生接口，后端聚合实现）：

| 接口 | 说明 | 关键字段 |
|------|------|----------|
| OptionChain | 期权T型报价 | underlying, calls[], puts[] |
| OptionQuote | 单个期权报价 | strikePrice, impliedVolatility |
| VolatilityData | 隐含波动率 | Black-Scholes模型参数 |

**关键发现**：
- 所有字段命名采用camelCase（如 `instrumentID`, `lastPrice`, `bidPrice1`）
- 期权相关字段在 InstrumentInfo 中：`optionsType`, `strikePrice`, `underlyingInstrID`
- 五档深度字段：`bidPrice1-5`, `askPrice1-5`, `bidVolume1-5`, `askVolume1-5`
